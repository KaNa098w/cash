# Маркированные упаковки в POS

Корзина хранится локально. Продажа: штрихкод товара → количество → POST `/organizations/pos/{key}/sales/marking-check` всей корзины → при необходимости DataMatrix → повторная проверка → оплата → POST `/sales`. Проверка не регистрирует упаковку, продажу или фискальный чек. Для DataMatrix сначала выбирается товар по обычному штрихкоду; GTIN и структуру маркировки проверяет backend.

Ответ содержит `data.ready` и результаты по `product_id`. Оплата разрешена только при `data.ready=true`, `ready=true` для всех позиций и наличии ответа для каждого товара. Снимок проверки включает магазин, терминал, активный чек и содержимое корзины. Любое изменение отменяет разрешение; проверка выполняется снова. После перезапуска разрешение не восстанавливается из локального черновика.

`open_quantity`, `missing_quantity`, `package_quantity` и `required_codes_count` берутся с сервера. Окно показывает количество, покрытые единицы и нехватку; запрашивает ровно указанное число новых кодов. Если открытой упаковки достаточно, сканирование не требуется. До разрешения оплаты основная кнопка предлагает «Проверить». При ошибке сети продажа не создаётся.

DataMatrix хранится и отправляется без канонизации: сохраняются `]d2`, GS-разделители и регистр. Вставка Cmd+V/Ctrl+V поддерживается; после вставки можно нажать Enter или кнопку проверки кода. Локально блокируются только точные дубли. Ответ `EXTRA_MARK_CODE` очищает новые коды позиции и повторяет проверку. При `MARK_CODE_CONFLICT` backend не указывает конкретный код: новые коды этой позиции очищаются и запрашиваются заново. При HTTP 422 ошибки `items.N.mark_codes.M` удаляют указанный код, показывают сообщение и запускают повторную проверку.

После подтверждения оплаты POS сохраняет UUID чека и снимок запроса на устройстве. Сервис синхронизации присваивает локальный номер один раз и сохраняет запрос в SQLite до POST. Повтор использует тот же номер, UUID и платежи. Неопределённый результат блокирует изменение и удаление исходного документа.

`MARKING_PACKAGE_CHANGED` запускает `marking-check` повторно. Корзина, количество и платежи остаются заморожены; разрешена коррекция только кодов маркировки. После проверки повторяется создание продажи с исходными идентификаторами. При отмене сканирования или ошибке сети сохраняется признак незавершённой проверки; «Продолжить» возобновляет этот же чек, включая после перезапуска. Повторная оплата не нужна.

При сетевой ошибке и восстановлении прерванного POST операция остаётся в очереди для сверки. Повтор сначала читает sync/pull. Если серверный документ найден по клиентскому UUID, POST не выполняется. `IDEMPOTENCY_CONFLICT` никогда не меняет UUID и не запускает повторный POST без разрешения конфликта. Автоматическая синхронизация также сохраняет это правило.

Серверные `mark_codes`, `marking_parts`, идентификаторы позиций и фискальный чек сохраняются как окончательные данные. Отклонённая онлайн-продажа не включается в завершённые продажи смены; возврат меняет локальные итоги после серверного подтверждения.

Возврат предлагает действие по причине и позволяет изменить его. Проверка кодов учитывает количество, проданное из каждой упаковки, и уже возвращённые части; один код может покрывать несколько штук. При отсутствии `marking_parts` в старой истории окончательная проверка остаётся backend. Повтор возврата сохраняет исходный запрос и UUID.

Фискализация отслеживается только GET-запросами. `pending` и `processing` продолжают опрос с серверным интервалом; `needs_review` и `failed` останавливают его и показывают дальнейшее действие. Печать фискального чека доступна только при `succeeded` и `printable=true`, включая печать из истории. PrintFormat сохраняет порядок `lines`; поддержаны `paper_kind` 0, 3, 12 и 13. Ошибка печати не превращает принятую продажу в новый черновик.

## Проверка

Команды: `flutter test --no-pub`, `flutter analyze --no-pub`, `git diff --check`.

Автотесты используют настоящий SQLite и управляемые ответы POS API. Проверяются повтор после запроса маркировки, сохранение UUID/номера/платежей, серверное распределение между упаковками, сетевой тайм-аут со сверкой, идемпотентность продаж и возвратов, одновременная отправка одного документа, восстановление после перезапуска, неизменяемость принятых документов, частичные возвраты, сохранение исходных кодов, предварительная проверка и фискальные статусы.

Для интеграционной приёмки на тестовом backend нужны:

1. Продажи 3, 2 и 5 штук из упаковки на 10: сканирование только при первом открытии; следующая продажа запрашивает новую упаковку.
2. Остаток 2, продажа 3: в ответе две части с количествами 2 и 1. Продажа большего количества проверяет несколько последовательных запросов новой упаковки.
3. Одновременная оплата на двух POS: проигравшая касса сохраняет оплату и обрабатывает `MARKING_PACKAGE_CHANGED`.
4. Возврат в старую упаковку при уже открытой новой: порядок расходования определяет backend, повторного сканирования ранее открытых упаковок нет.
5. Разрыв соединения после регистрации продажи/возврата: sync/pull возвращает UUID исходного документа, повторного POST нет.
6. Ответы Webkassa `pending → processing → succeeded`, `failed`, `needs_review`; фактическая печать на используемых принтерах.

Эти интеграционные сценарии требуют работающего backend, Webkassa и оборудования; локальные тесты не подтверждают серверный алгоритм распределения упаковок или физическую печать.
